# Usage / Audit MVP 职责边界 v2

## 1. 目的

将当前 MVP 的对外产品面收敛为 `Usage` 与 `Audit` 两类，并明确其目标、角色、动作和禁止事项，防止未来功能蔓延与术语漂移。

本文件只定义 workspace 业务面中的 `Usage` 与 `Audit`。系统超级管理员入口、workspace 登录入口和 workspace 配置模型，另见 `system-workspace-identity-entry-mvp-v1.md`。

补充约束（2026-03-11）：

2. 历史上归入 `Runtime` 的用户可见状态记录、配置记录与诊断信息，如仍然保留，必须并入 `Audit`。

## 2. 页面职责

### 2.1 Usage（用户）

定位：用户自助查看“我当前在各个资源上的用量与限制消耗程度”。

允许：

1. 今日请求/错误/Token 及时间趋势展示。
2. 按 endpoint 分组展示限制数据（每个 endpoint 独立卡片或 tab）。
3. 每个 endpoint 内固定展示 `rate limit` / `spending limit` 两组。
4. 每组按时间窗口展示（如 `minute` / `5h` / `day`，无窗口细分时回退 `current`）。
5. 以低心智方式展示消耗程度与剩余程度。
6. 刷新与基础时间范围切换（具体窗口以当前后端可支持范围为准）。

不允许：

1. 管理员审计处置动作。
2. 系统状态与配置变更主表。
3. 高级/详细模式切换。
4. 以单一聚合进度条替代 endpoint 维度信息。
5. 跨 endpoint 聚合 `rate` / `spending` 并输出统一“总剩余限制”或统一百分比。
6. 将资源策略配置投影伪装成实时消耗快照。

### 2.2 Audit（管理员）

定位：管理员统一查看资源、配置、状态与异常事件记录的审查台。

允许：

1. 项目整体审计事件检索与证据追溯。
2. 资源配置变更记录查看。
3. 资源状态变化与异常事件查看。
4. request/decision/trace 的必要追溯。
5. 从审计详情跳转资源策略、成员、用量等相关处置页面。

不允许：

1. 承担用户日常“我的用量”主路径。
2. 演化为 DevOps 发布、发布门禁或运维编排平台。
3. 暴露底层实现术语并要求用户理解内部机制对象。
4. 承担复杂资源编排台、创建台、模拟台的职责。

## 3. 权限与入口

1. `Usage`：`project:endpoint:use`
2. `Audit`：`project:audit:read`

入口约束：

1. 普通用户默认只暴露 `Usage`。
2. 管理员默认暴露 `Audit` 与 `Usage`。
3. 不再为 MVP 暴露独立 `Runtime` 导航入口。

## 4. 术语约束

1. `Usage` 统一称“用量视图”。
2. `Audit` 统一称“审计”。
3. `Runtime` 只允许作为实现或合同层语义，不再作为独立产品面命名。
4. 资源约束统一使用 `rate limit` / `spending limit`；禁止新增 `quota` 新命名（历史字段仅做解析，不对外扩散）。
5. `Usage` 仅表达用户在具体资源与具体窗口上的消耗程度，不表达跨资源统一总量。
6. 不再使用 `release-ops` 作为页面名、路由名、入口名或可见产品术语。
7. 不得将 `release` / `engineering gate` / `rollout` 作为平台对外能力名；这些术语只允许出现在项目研发流程与工程验收上下文。
8. 以下术语不再作为当前 MVP 的前端产品对象或 UX 术语：
- `guardrails`
- `probe`
- `alias`
- `combo`
- `routing`
- `activation`

## 5. 变更准入检查（必须全通过）

1. 新需求是否明确落在 `Usage` 或 `Audit` 之一？
2. 是否引入了跨边界动作（例如在 Usage 加审计处置）？
3. 是否新增了双重语义（同一能力在多个页面主路径出现）？
4. 文档、i18n、测试 ID 是否与新的双模块边界一致？
5. 是否把实现细节对象重新抬升成了用户需要理解的概念？

若任一项不通过，变更不得进入实现。
