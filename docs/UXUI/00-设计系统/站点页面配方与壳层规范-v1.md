# 站点页面配方与壳层规范 v1

Status: `active`
Depends on: [`DESIGN.md`](../../../DESIGN.md)
Scope: `interaction / product behavior`
Does not define: `global tokens / route truth / engineering gates`

## 1. 目标

把 AgentSmith 全站页面收敛成少量可复用的 recipe family，避免不同页面家族各自发明壳层、卡片堆和说明页语法。

本文件只定义页面家族与壳层边界，不定义产品对象、路由真相、权限或后端契约。

## 2. 基本规则

1. 每个 route 只能归属一个 recipe family。
2. 页面优先使用共享 primitives 和共享 shell，不能先画一个页面私有壳再往里塞内容。
3. 任何 split / aside / card stack 都必须先证明它能降低心智负担，否则默认改成单列或连续 sheet。
4. 页面 recipe 不能突破 [`DESIGN.md`](../../../DESIGN.md) 中的 CTA、state、light/dark parity 和 visual review 约束。

## 3. 站点级 recipe family

### 3.1 `public_auth_single`

适用：

1. workspace select
2. system login
3. workspace login
4. join / invite accept
5. desktop auth request / complete

要求：

1. 单主列优先。
2. 只允许一块轻量辅助说明，不允许独立右栏与 chooser card stack 同时出现。
3. workspace select 以安静列表为主，不做 dashboard chooser。
4. complete / success 页面默认是收口页，不再反向制造第二层说明壳。

禁止：

1. 双栏 landing page 语法作为默认形态。
2. 把选 workspace 做成大面积卡片墙。
3. 在 auth flow 中引入 dashboard summary strip。

### 3.2 `public_auth_split`

适用：

1. 仅在辅助说明对主任务有明显帮助时使用

要求：

1. 主任务必须在主列完成。
2. 右侧内容只能是 muted helper，不得成为第二个主任务。
3. split layout 必须比单列更安静，而不是更像 marketing page。

禁止：

1. 任何需要用户来回对照的复杂配置页使用该 recipe。
2. 用 split layout 包装完成页、确认页或 workspace chooser。

### 3.3 `work_surface_standard`

适用：

1. workspace overview
2. project overview
3. agents
4. endpoints

要求：

1. 顶部只保留一套主 header 语法。
2. 页面主体是一个主要工作面，辅以低噪声的工具或筛选条。
3. 使用空间、分隔线和排版组织层级，不依赖多层 summary card。

禁止：

1. 二次标题带与主 header 并列抢注意力。
2. 页面内再包一层 page shell。
3. 用 dashboard KPI 样式替代任务入口。

### 3.4 `work_surface_immersive`

适用：

1. chat
2. agent-tasks
3. files

要求：

1. 只保留一个真正的工作流 header。
2. utility strip 只能服务上下文切换、状态和必要动作。
3. 内容区优先连续工作面，不做 decorative 叠层。

禁止：

1. 重复 page header。
2. 让 shell 比工作内容更醒目。
3. 在工作流页面引入 page-local gradient、glow 或高噪声说明块。

### 3.5 `settings_sheet`

适用：

1. workspace settings
2. project settings
3. user profile
4. api keys
5. personal connections

要求：

1. 使用连续 sheet 或连续 section，而不是 dashboard panel stack。
2. 以 section title + divider 组织层级。
3. 主动作清晰，次级动作安静。

禁止：

1. summary tile / KPI strip 抢占首屏。
2. 多个卡片同时作为同权重入口。
3. 让设置页看起来像运营大盘。

### 3.6 `governance_table_detail`

适用：

1. members
2. usage
3. audit
4. resource policy

要求：

1. 主体必须有一个明显 dominant table / list。
2. 详情只在需要时展开为 drawer / sheet / inline detail。
3. 信息密度可以高，但结构必须安静。

禁止：

1. 用 summary card 代替表格或列表。
2. 用多层 card 把治理页面做成 dashboard。
3. 让 secondary detail 抢走主列表注意力。

### 3.7 `system_admin_detail`

适用：

1. system workspaces
2. system workspace create
3. system info

要求：

1. list-detail 或 editor-detail 是默认结构。
2. create flow 必须有单一主推进动作。
3. system info 只展示系统级基础状态，不扩展成运维大盘。

禁止：

1. 双主栏争夺注意力。
2. 进入 system 页后再出现业务 dashboard 语法。
3. 把 system 管理页做成营销式介绍页。

### 3.8 `overlay_dialog`

适用：

1. 删除确认
2. 危险操作确认
3. 单项选择
4. 极轻量输入

要求：

1. 只承担短、快、一次性的动作。
2. 不可把重内容表单塞进 Dialog。

### 3.9 `overlay_sheet`

适用：

1. 多字段表单
2. 分组配置
3. 权限 / 配额 / ACL
4. 需要对照主列表的编辑场景

要求：

1. 右侧浮层作为主编辑面。
2. 固定头部、可滚动内容、固定底部动作栏。
3. 复杂创建 / 编辑默认先考虑此 recipe。

## 4. Shell 约束

1. Topbar、Sidebar、PageHeader、WorkbenchBar 只能作为同一 recipe family 的一部分出现。
2. 页面不能自己发明新的 shell 外框来包裹现有壳层。
3. shell 的存在价值是降低歧义，不是增加存在感。
4. 如果某个 shell 让用户先理解结构再做事，它就是过重的。

## 5. 收敛原则

1. 不确定时选择更低噪声的 recipe。
2. 同一产品对象在不同页面家族里可以有不同密度，但不能有不同语法。
3. 只要页面能用单列、连续 sheet、dominant table 解决，就不要上 split、chooser card 或 dashboard stack。
4. recipe family 的目标是减少用户需要重新学习界面的次数。
