# AgentSmith 项目宪法

本文档用于约束当前产品目标、边界与治理原则，避免范围漂移。

## 一、定位

AgentSmith 是 MBOS 的企业级控制面，服务工作区与项目中的 AI 使用、资源治理与审计。

当前产品职责：

1. 企业级 AI 智能体使用与管理
2. 项目级 AI 资源治理
3. 项目级审计与用量追踪

## 二、范围

在范围内：

1. 认证与身份
2. 工作区与项目
3. Chat / Notebook / Files / Agents / Endpoints
4. 资源策略（project scope）
5. 成员与凭据
6. 审计与用量

不在范围内：

1. DevOps 发布编排与发布管理平台能力
2. 组织级统一资源治理总控（跨 project 汇总治理）
3. Chat/Notebook 独立限额体系
4. 文件级策略

说明：如仓库内出现 `release` / `engineering gate` 命令命名，属于项目研发流程术语（验收/排障/报告），不构成产品功能范围；`permission gate` 仅表示产品内权限门禁语义。

补充约束：如必须描述底层技术职责，应使用更具体的职责名，例如 `agent execution`、`notebook execution`、`model request execution`、`model catalog sync`、`project pricing config`，避免继续使用模糊的 `Runtime` 统称。

## 三、治理主线

唯一主线：项目级 LLM endpoint 统一约束链路。

统一约束适用面：

1. Chat
2. Notebook
3. 用户 API 调用

约束与证据：

1. rate limit
2. spending limit
3. policy/audit evidence
4. usage evidence

## 三点五、Usage / Audit 边界（强约束）

`Usage`（用户视角）：

1. 唯一目标是“看我的用量与剩余限制”。
2. 提供低心智的单一视图，不承载管理员排障、审计分析、治理处置。
3. 不提供“高级模式/分析模式/审计模式”切换。
4. 不做跨资源统一汇总。

`Audit`（管理员视角）：

1. 唯一目标是“看资源、配置、状态与异常事件记录，并完成审查与追溯”。
2. 面向项目整体与成员行为证据，支持 request/decision/trace 的必要追溯。
3. 管理员分析入口固定在 Audit，不回流到 Usage。
4. 原本属于运行时状态记录、配置记录与技术诊断的用户可见内容，如仍然保留，统一并入 Audit。

禁止边界漂移：

1. 禁止把系统扩展成第三个模糊产品面；MVP 对外只保留 `Usage` 与 `Audit`。
2. 禁止在 Usage 中新增面向管理员的排障入口和治理动作。
3. 禁止把 Audit 演化为复杂资源编排台、模拟台或 DevOps 发布台。
4. 禁止将实现细节对象抬升为用户需要理解的核心概念。

## 四、最小产品对象模型（强约束）

当前 MVP 只允许前端围绕以下对象建模：

1. `Resource`
2. `UsageRecord`
3. `LimitRecord`
4. `ConfigurationChange`
5. `SystemEvent`

禁止继续把以下对象作为前端产品对象和 UX 术语扩张：

1. `guardrails`
2. `probe`
3. `alias`
4. `combo`
5. `routing`
6. `activation`

## 五、架构与权限原则

1. 后端是唯一权威；前端门禁不替代后端鉴权。
2. 权限判断只认 permission token，不以角色名做运行时门禁。
3. URL 是工作区/项目上下文真相源。
4. 路由参数必须先校验再用于请求和门禁。

## 六、工程约束

1. 生产代码禁止 `any`。
2. 用户可见文案必须 i18n 化。
3. 受保护路由必须有门禁契约检查。
4. 合约优先，接口与前端类型保持一致。
5. 默认 E2E 门禁固定为功能链路（`smoke + chromium`）；visual 仅作为手动基线流程。

## 七、防漂移清单

禁止：

1. 把系统扩展为发布管理/DevOps 平台
2. 引入组织级治理总控叙事作为当前主线
3. 用角色名/治理分组名替代权限 token 鉴权
4. 在无合同定义前新增治理维度与策略对象
5. 将 visual baseline 缺失/差异作为 MVP 默认发布阻断条件

## 八、MVP 收敛与 UX 约束

产品与治理能力必须遵循“最小可用、可审计、可闭环”三条线，不为完整性而扩张功能面。

范围收敛原则：

1. 治理能力仅围绕项目级 LLM endpoint 约束链路建设，不新增并行治理体系。
2. 新功能必须直接服务现有主线（AI 使用、资源配置与限额、审计追踪）。
3. 不能以“未来可能需要”为理由进入 MVP；超出当前闭环的问题进入待规划，不进入实现。

UX 降负原则：

1. 默认优先“少步骤完成关键任务”（查看用量、查看记录、定位异常、执行处置）。
2. 新交互需复用现有信息结构与稳定术语，避免引入新的概念层级。
3. 同一调查链路中的关键信息必须可复制、可跳转、可复现，不要求用户跨页手工拼接上下文。
4. 默认视图与默认参数应优先降低认知负担，不引入要求用户理解实现细节的入口。

## 九、变更准入标准

任何需求进入开发前，至少同时满足：

1. 与第二章范围和第三章治理主线一致；
2. 不新增 MVP 外产品叙事或能力对象；
3. 能明确降低操作路径复杂度或提升审计闭环效率；
4. 文档、合约、代码、测试可同步落地。
