# AgentSmith 项目宪法

本文档用于约束当前产品目标、边界与治理原则，避免范围漂移。

## 一、定位

AgentSmith 是 MBOS 的企业级多租户控制面，服务系统级工作区管理、工作区内项目级 AI 使用、资源治理与审计。

当前产品职责：

1. 系统级工作区生命周期与租户配置管理
2. 企业级 AI 智能体使用与管理
3. 项目级 AI 资源治理
4. 项目级审计与用量追踪

## 二、范围

在范围内：

1. 认证与身份
2. 工作区与项目
3. 系统超级管理员与工作区管理员
4. Chat / Agent tasks / Files / Agent Runners / Endpoints
5. 资源策略（project scope）
6. 成员与凭据
7. 审计与用量

不在范围内：

1. DevOps 发布编排与发布管理平台能力
2. 组织级统一资源治理总控（跨 project 汇总治理）
3. Chat/Agent tasks 独立限额体系
4. 文件级策略

说明：如仓库内出现 `release` / `engineering gate` 命令命名，属于项目研发流程术语（验收/排障/报告），不构成产品功能范围；`permission gate` 仅表示产品内权限门禁语义。

补充交付边界：

1. `AgentSmith Web` 与 `AgentSmith Desktop` 是两个独立交付面，不共享发布节奏。
2. 两者只通过显式合同、地址真相与验收证据对齐，不允许通过“必须同版同时发布”的隐式假设耦合。
3. Desktop 发布问题不得阻断无关 Web 变更发布；Web 发布问题也不得阻断无关 Desktop 版本交付。若合同变更影响对方，必须先改合同与验证，再做对应发布安排。

补充约束：如必须描述底层技术职责，应使用更具体的职责名，例如 `agent execution`、`notebook execution`、`model request execution`、`model catalog sync`、`project pricing config`，避免继续使用模糊的 `Runtime` 统称。

身份边界补充：

1. Authn（认证）由 IdP 提供；当前每个 workspace 绑定独立 Keycloak。
2. Authz（授权）由 AgentSmith 提供并执行。
3. 系统级登录入口与 workspace 业务入口必须完全分离。
4. 系统超级管理员账户在系统启动前以配置方式注入；默认凭据为 `mbos-admin / mbos-admin`。

## 三、治理主线

唯一主线：项目级 LLM endpoint 统一约束链路。

这里的“治理”是产品能力，只限于项目级 LLM endpoint 的策略、用量与审计闭环。release / engineering gate 等研发验收手段，不得包装成产品能力、用户概念或长期研发主线。

统一约束适用面：

1. Chat
2. Agent tasks
3. 用户 API 调用

约束与证据：

1. rate limit
2. spending limit
3. policy/audit evidence
4. usage evidence

## 三点五、Usage / Audit 边界（强约束）

`Usage`（用户视角）：

1. 唯一目标是“看我的用量与剩余限制”。
2. 提供低心智的单一视图，不承载管理员排障、审计分析、治理处置。
3. 不提供“高级模式/分析模式/审计模式”切换。
4. 不做跨资源统一汇总。

`Audit`（管理员视角）：

1. 唯一目标是“看资源、配置、状态与异常事件记录，并完成审查与追溯”。
2. 面向项目整体与成员行为证据，支持 request/decision/trace 的必要追溯。
3. 管理员分析入口固定在 Audit，不回流到 Usage。
4. 原本属于运行时状态记录、配置记录与技术诊断的用户可见内容，如仍然保留，统一并入 Audit。

系统与工作区边界：

1. `Usage` 与 `Audit` 是当前项目业务面的治理主线，不包含系统级工作区生命周期管理。
2. 工作区级 overview 不得扩张为无真实后台支撑的运营指标大盘。
3. workspace overview 应收敛为工作区入口与项目导航，不承载伪运营指标。

禁止边界漂移：

1. 禁止把系统扩展成第三个模糊产品面；MVP 对外只保留 `Usage` 与 `Audit`。
2. 禁止在 Usage 中新增面向管理员的排障入口和治理动作。
3. 禁止把 Audit 演化为复杂资源编排台、模拟台或 DevOps 发布台。
4. 禁止将实现细节对象抬升为用户需要理解的核心概念。

## 四、最小产品对象模型（强约束）

当前 MVP 只允许前端围绕以下对象建模：

1. `Resource`
2. `UsageRecord`
3. `LimitRecord`
4. `ConfigurationChange`
5. `SystemEvent`

禁止继续把以下对象作为前端产品对象和 UX 术语扩张：

1. `guardrails`
2. `probe`
3. `alias`
4. `combo`
5. `routing`
6. `activation`

工作区与身份对象（系统级）：

1. `SystemAdmin`
2. `Workspace`
3. `WorkspaceAdmin`
4. `ProjectCreator`
5. `ProjectOwner`
6. `ProjectAdmin`
7. `Project`
8. `IdentityProviderConfig`
9. `WorkspaceDataConfig`

服务商中立建模原则：

1. AgentSmith 只建模服务商中立的资源、身份、凭据引用、执行能力和审计证据。
2. 具体 SaaS、协作、工单、代码托管或消息服务商不得成为当前 MVP 的一等产品对象、默认配置维度、权限语义或 runner skill 成功路径。
3. 外部服务接入只能通过合同定义的中性配置、Project secrets、请求级只读投影和审计证据表达；具体服务商适配不进入当前默认产品路径。

## 五、架构与权限原则

1. 后端是唯一权威；前端门禁不替代后端鉴权。
2. 权限判断只认 permission token，不以角色名做运行时门禁。
3. URL 是工作区/项目上下文真相源。
4. 路由参数必须先校验再用于请求和门禁。
5. `WorkspaceAdmin`、`ProjectCreator`、`ProjectOwner`、`ProjectAdmin` 不是权限系统的一等公民；它们只作为默认组、关系标签和管理 UI 对象存在。
6. owner/admin/creator 等关系只能作为权限派生来源，不能在页面与接口中散落地替代 permission check 成为最终门禁真相。

身份与入口原则：

7. 系统超级管理员是唯一系统级高权限入口。
8. 只有系统超级管理员可以创建、配置、停用或删除 workspace。
9. 只有系统超级管理员可以查看 workspace 级系统信息、依赖服务配置与租户隔离结果。
10. workspace 管理员不管理 workspace 生命周期，不管理 IdP，不管理底层租户隔离配置。
11. workspace 管理员负责 workspace 下 project 创建能力的授予，以及必要时的 owner 强制转让。
12. workspace 成员不在 AgentSmith 内做成员生命周期管理；只要存在于该 workspace 绑定的 IdP 中，即视为合法认证用户。
13. 普通业务用户必须先选择 workspace，或先进入某个 workspace URL，再进入该 workspace 登录页。
14. 系统超级管理员入口必须与 workspace 业务登录入口完全分离。
15. 具备 workspace 级 project 创建权限的用户，在创建 project 后自动成为该 project 的 `ProjectOwner`。
16. `ProjectOwner` 拥有 project 生命周期、owner 转让与 `ProjectAdmin` 指定权限。
17. `ProjectAdmin` 只负责 project scope 内治理，不负责删除 project、owner 转让或继续授予管理权限。

## 六、工程约束

1. 生产代码禁止 `any`。
2. 用户可见文案必须 i18n 化。
3. 受保护路由必须有门禁契约检查。
4. 合约优先，接口与前端类型保持一致。
5. 默认工程门禁固定为功能链路验证；视觉验证属于独立证据通道，由单独的视觉验证流程负责。
6. 源码根目录不得承载 lane 运行态或 generated coordination state。
7. 验证必须按层分离；环境失败不得伪装成功能回归。
8. ownership 未证实前不得 destructive cleanup；自愈必须以 authority 为前提。
9. 工程治理克制：工程治理从属于功能交付；新增和既有 gate/docs/script 都必须按当前功能、安全、合同、真实运行/发布风险与用户低心智收益复核。不能为完整性、仪式感或未来可能需要新增长期治理；低收益项默认删除或归档，必要时降级为 focused diagnostic，只有仍承担明确风险控制时才保留长期 gate；反过度治理本身不得演化为新的流程、看板或 gate。

## 七、防漂移清单

禁止：

1. 把系统扩展为发布管理/DevOps 平台
2. 引入组织级治理总控叙事作为当前主线
3. 用角色名/治理分组名替代权限 token 鉴权
4. 在无合同定义前新增治理维度与策略对象
5. 在未经过发布规则显式声明前，将 visual baseline 缺失/差异升级为默认发布阻断条件
6. 将具体服务商适配升级为默认一等配置、凭据模型、runner skill 或正式成功路径
7. 以“反过度治理”为名新增治理体系、看板、gate 或流程

## 八、MVP 收敛与 UX 约束

产品与治理能力必须遵循“最小可用、可审计、可闭环”三条线，不为完整性而扩张功能面。

范围收敛原则：

1. 治理能力仅围绕项目级 LLM endpoint 约束链路建设，不新增并行治理体系。
2. 新功能必须直接服务现有主线（AI 使用、资源配置与限额、审计追踪）。
3. 不能以“未来可能需要”为理由进入 MVP；超出当前闭环的问题进入待规划，不进入实现。

UX 降负原则：

1. 默认优先“少步骤完成关键任务”（查看用量、查看记录、定位异常、执行处置）。
2. 新交互需复用现有信息结构与稳定术语，避免引入新的概念层级。
3. 同一调查链路中的关键信息必须可复制、可跳转、可复现，不要求用户跨页手工拼接上下文。
4. 默认视图与默认参数应优先降低认知负担，不引入要求用户理解实现细节的入口。
5. 产品与文档优先使用直观表述，如 `system 管理侧`、`用户访问入口`、`工作区发布状态`、`工作区是否可访问`、`后端基础初始化`。
6. `control plane`、`runtime`、`orchestrator`、`foundation` 等工程术语不得作为默认产品叙事；如确有必要，必须先给出当前语境下的直白解释。
7. 不使用 `registry` 作为泛化产品术语；涉及 system 管理侧保存的数据时，统一表述为 `工作区配置记录`、`工作区清单` 或 `历史工作区配置数据`。

工作区配置约束：

5. workspace 创建时，底层租户隔离命名应由系统根据预配置 substrate 规则自动生成，不要求系统超级管理员手工输入数据库名、collection 名或 prefix。
6. 系统仅向系统超级管理员暴露系统信息页，用于查看依赖服务 URL、租户命名规则与底层配置结果，不将其扩张为运维大盘。
7. 身份与权限管理默认使用 `Email 选人，ID 落库`：界面以 email 作为主识别信息，系统内部唯一主键保持 `user_id = Keycloak sub`。

## 九、变更准入标准

任何需求进入开发前，至少同时满足：

1. 与第二章范围和第三章治理主线一致；
2. 不新增 MVP 外产品叙事或能力对象；
3. 能明确降低操作路径复杂度或提升审计闭环效率；
4. 文档、合约、代码、测试可同步落地。

补充原则：需求优先回到核心用户路径和当前主线，工程交付机制只作为风险控制，不成为产品路线。
