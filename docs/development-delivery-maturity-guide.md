# 开发团队交付成熟度硬性指南（执行版）

## 1. 目的与适用范围

本指南用于约束 AgentSmith 研发交付质量，确保功能、治理、可运营性同步达标。
适用于所有涉及产品功能、权限、路由、运行治理、测试与发布的代码提交。

## 2. 强制执行规则

1. 先合约后实现
- 新功能必须先明确对象模型、权限点、URL 真相源、API 合约。
- 未定义权限点、未定义 URL 行为、未定义错误语义时，不得进入编码。

2. 权限门禁一票否决
- 仅允许 token/permission 点做门禁，禁止角色名硬编码门禁。
- 禁止在 hook 中短路写法（例如 `useHasPermission('a') || useHasPermission('b')`）；必须分别判断后组合。

3. URL 与状态一致性强约束
- URL 是运行时真相源，tab/filter/分页等可分享状态必须可从 URL 还原。
- 权限纠正、默认回退等行为必须有明确规范，并补齐单测与 E2E 断言。

4. 类型与质量底线
- 生产代码禁止 `any`。
- 路由参数必须执行校验（如 workspace/project 参数）。
- 死代码、无效 props、无用 import 不允许进入主干；lint 必须 0 error。

5. 测试分层必须齐全
- 至少覆盖：`type/contract`、`unit`、`integration`、关键路径 `e2e`。
- UI/路由/权限修复必须补回归用例，防止同类问题复发。
- test id 必须稳定、唯一、可读，避免脆弱选择器。

6. 提交与 PR 证据化
- 每个 PR 必须附“变更意图 + 风险点 + 回归范围 + 验证证据”。
- 证据至少包含：`lint`、相关 `unit`、相关 `e2e` 通过结果。
- 仅“功能看起来可用”不算完成，必须可复现通过门禁。

7. 失败处理机制
- 任一门禁失败立即阻断合并，先修复再推进。
- 对回归问题必须补“防复发测试”，否则不关闭问题。
- 对残余风险必须给出 owner、截止时间与后续动作。

8. 分支交付完成定义（DoD）
- 功能正确：行为符合合约与权限策略。
- 治理正确：门禁、审计、错误处理路径完整。
- 质量正确：lint/类型/测试全部通过。
- 运行正确：清理残留进程，测试环境可重复执行。
- 文档正确：必要说明与变更记录同步更新。

9. 本项目高频问题专项要求
- Runtime Console 相关变更必须验证：tab 切换、URL 纠正、历史前进后退、权限回退。
- 任何“临时修复”进入主干前必须重构为可维护实现，并清理无用代码。
- warning 仅在“已评估无风险且有记录”时可接受；未知 warning 视为缺陷线索继续追踪。

10. 合并前硬门禁命令（最小集）

```bash
npm run lint
npx tsc --noEmit
npm test
# 涉及 runtime-console 域时必须执行（专项回归，不属于默认 MVP release gate）
npx playwright test --project=chromium e2e/legacy/runtime-console.spec.ts
```

## 3. 开发团队明确执行指令

1. 从下一次提交起，以上 10 条作为强制标准；不满足即拒绝合并。
2. 每个 PR 必须附完整证据链，不再接受“描述性通过”。
3. 对历史反复问题（权限/URL/回归）执行“修复 + 防复发测试”双交付。

## 4. 评审检查清单（Reviewer Quick Check）

- 是否有明确权限点与门禁实现，且未使用角色名硬编码？
- URL 是否可还原页面关键状态，权限回退是否可解释且可测试？
- 是否新增或更新了必要的单测与 E2E？
- lint/类型检查/测试证据是否完整可复现？
- 是否存在无用代码、无效 props、无效依赖与未处理 warning？
- 文档是否与行为一致（含限制、风险、回退语义）？

## 5. 配套模板

- PR 描述模板：`/.github/PULL_REQUEST_TEMPLATE.md`

## 6. Main 分支持续开发约束

适用于“直接在 `main` 分支持续开发”的工作模式，作为最低执行纪律：

1. 单主题提交
- 每次改动只解决一个主题问题（功能、修复或重构之一），避免混合提交。

2. 本地门禁先通过再提交
- 提交前必须通过：`npm run lint && npx tsc --noEmit && npm test`。
- 涉及 runtime-console、权限、URL 状态时，额外必须通过专项回归（不并入默认 MVP gate）：
  `npx playwright test --project=chromium e2e/legacy/runtime-console.spec.ts`。

3. 提交信息和说明最小要求
- 提交信息采用 `type(scope): summary`。
- 提交说明必须包含：风险点、执行过的验证命令、结果摘要。

4. 回归处理优先级
- 一旦发现回归，立即停止新需求开发。
- 必须先补“防复发测试”，再实施修复。

5. 环境与工作区卫生
- 开始开发前确认无残留服务进程、无无关脏改动。
- 保持工作区可重复验证，避免“环境偶然通过”。
