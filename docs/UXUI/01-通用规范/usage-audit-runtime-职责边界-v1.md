# Usage / Audit / Runtime 职责边界 v1

## 1. 目的

将 `Usage`、`Audit`、`Runtime` 三个页面族的目标、角色、动作和禁止事项固定为明确边界，防止未来功能蔓延与术语漂移。

## 2. 页面职责

### 2.1 Usage（用户）

定位：用户自助查看“我的用量”和“剩余限制”。

允许：

1. 今日请求/错误/Token 及时间趋势展示
2. endpoint 限制剩余量展示
3. 刷新、7/30 天切换

不允许：

1. 管理员审计处置动作
2. 运行时深度诊断面板
3. 高级/详细模式切换

### 2.2 Audit（管理员）

定位：管理员审计与治理处置台。

允许：

1. 项目整体审计事件检索与证据追溯
2. request/decision/trace 调查链路
3. 跳转成员、资源策略、用量视图执行处置

不允许：

1. 承担用户日常“我的用量”主路径
2. 以 Runtime 技术指标替代审计事件语义

### 2.3 Runtime（管理员）

定位：运行时可观测与技术诊断台。

允许：

1. provider/model/fallback/error/pricing 信号分析
2. 请求级 runtime fact 明细钻取
3. 从诊断上下文跳转到审计与资源策略

不允许：

1. 作为用户用量首页
2. 承担审计事件主表与治理处置主流程

## 3. 权限与入口

1. `Usage`：`project:endpoint:use`
2. `Audit`：`project:manage`
3. `Runtime`：管理员诊断入口（由后端权限策略约束）

入口约束：

1. 普通用户不暴露管理员诊断/审计入口
2. 管理员可访问三者，但入口职责不混合

## 4. 术语约束

1. `Usage` 统一称“用量视图”，不再使用 `lite/advanced` 术语。
2. `Audit` 统一称“审计与治理”。
3. `Runtime` 统一称“运行时可观测/诊断”。

## 5. 变更准入检查（必须全通过）

1. 新需求是否明确落在三者之一？
2. 是否引入了跨边界动作（例如在 Usage 加审计处置）？
3. 是否新增了双重语义（同一能力在多个页面主路径出现）？
4. 文档、i18n、测试 ID 是否与目标边界一致？

若任一项不通过，变更不得进入实现。
