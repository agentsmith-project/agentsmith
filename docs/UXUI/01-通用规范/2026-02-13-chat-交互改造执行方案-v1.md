# Chat 交互改造执行方案（P0/P1）

## 1. 背景与目标
- 当前 Chat 已可用，但在“无活跃会话”“端点能力不匹配”“上传路径偏长”场景下存在明显心智负担。
- 目标：将 Chat 从“功能可用”提升到“行为可预期、路径最短、失败可恢复”。

## 2. 设计原则
- 先约束再操作：不可用功能不应伪可用。
- 能力驱动 UI：端点能力决定界面是否展示对应入口。
- 空态可执行：空状态必须给直接可点击动作。
- 失败可恢复：错误提示必须附带下一步。

## 3. 范围与优先级
### P0（本轮必须）
1. 无 active thread 时，明确引导与禁用语义一致。
2. 按 endpoint capability 控制附件入口显示/禁用。
3. 在文本端点前置拦截图片/文件上传，直接给清晰提示。

### P1（下一轮）
1. 输入区支持拖拽上传和粘贴图片上传。
2. 输入区状态机统一（no_thread/need_endpoint/ready/uploading/streaming/error）。
3. 线程列表增强“后台生成中”指示。

## 4. P0 详细改造点
### 4.1 无 active thread 交互
- 右上模型区不展示模型选择器，改为“新建聊天”主操作。
- 中央空态展示双路径：
  - 新建聊天
  - 从左侧选择已有会话
- 输入区与发送操作在无会话时不可用；原因提示为“请先创建或选择会话”。

### 4.2 端点能力驱动附件入口
- 仅当当前端点启用 `multimodal_completion` 时展示附件入口（本地上传、文件库选择）。
- 非多模态端点：
  - 隐藏附件入口（或禁用并显示原因提示）。
  - 发送区文案提示“当前端点仅支持文本对话”。

### 4.3 前置拦截
- 当端点不支持多模态时：
  - 本地文件选择：拦截并 toast 提示。
  - 文件库添加：拦截并 toast 提示。
- 避免“上传成功但模型看不到”的后置失败体验。

## 5. 验收标准（DoD）
1. 删除最后一个 thread 后，页面不出现“可见但不可理解”的无效模型/输入状态。
2. 非多模态端点看不到附件操作入口，且有明确原因提示。
3. 非多模态端点尝试上传时立即提示，不进入上传队列。
4. 多模态端点附件功能正常（预览、发送、上游 payload）。
5. 中英文文案同步。
6. 单测覆盖关键状态分支。

## 6. 测试清单
- `ChatHeader`：无会话时 CTA 与提示文案。
- `ChatMainPane`：空态与禁用提示。
- `Composer`：能力开关下附件入口显示逻辑。
- `use-chat-composer-actions`：能力不满足时上传拦截。

## 7. 风险与回滚
- 风险：历史测试默认“无会话仍可选模型”语义需要更新。
- 回滚：仅涉及 Chat 前端组件与文案，回滚成本低，可按组件维度回退。
