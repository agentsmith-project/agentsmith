# AgentSmith 项目宪法

本文档是 AgentSmith 的**最高指导文件**，用于约束产品目标、设计风格与功能范围，防止长期演进中的目标漂移与范围蔓延。所有新需求、重构与设计决策应与此宪法一致；冲突时以本宪法为准，并优先通过修订宪法达成共识，而非在局部妥协。

**宪法定位**：本宪法只规定**思想、方法论与概念**，不规定具体技术实现、文件路径、工具命令或配置。当前实现细节见 AGENTS.md、DEVELOPMENT.md 及 `docs/contracts/`、`docs/UXUI/` 下的合约与规范；技术栈或实现方式变更时，只要仍符合本宪法之思想与方法论，无需修宪。

---

## 一、项目定位与愿景

### 1.1 定位

AgentSmith 是 **MBOS（Microservices-Based Agent System）的企业级控制面**，面向工作区与项目下的 AI 智能体、AI 资源与运行治理进行使用、配置、观测与治理。

- **核心价值**：工作区/项目隔离、智能体使用与资源管理、资源治理与审计、多语言一致体验。
- **用户心智**：专业、克制、高效的后台管理工具，带适度 AI 标识，避免娱乐化或过度装饰。

更准确地说，AgentSmith 同时承担三层产品职责：

1. **企业级 AI 智能体使用与管理平台**
2. **AI 资源治理平台**
3. **项目级资源治理与审计控制面**

### 1.2 非目标

- 不是面向终端消费者的 ToC 产品，不追求营销型视觉或强品牌露出。
- 不是通用低代码/无代码平台，功能边界以「工作区 → 项目 → 资源/智能体/成员/审计」为主。
- 不替代后端鉴权与策略执行；前端门禁仅为体验优化，**后端为唯一权威**。

## 二、产品范围与边界

### 2.1 思想：边界即承诺

产品范围是**对用户与系统的承诺**：在范围内的能力必须被支持、可治理、不随意收缩；在范围外的能力不得以「顺手做了」的方式悄悄进入，以免目标与维护成本漂移。

### 2.2 在范围内（概念边界）

以下领域属于产品承诺范围；具体能力与权限词汇以合约为准。

| 领域 | 概念说明 | 边界思想 |
|------|----------|----------|
| 认证与身份 | 登录、工作区选择、个人资料、用户级 API Key | 身份与工作区成员由 IdP 负责；项目及资源级授权由 MBOS 域策略决定 |
| 工作区 | 工作区列表与设置、治理分组 | 治理分组仅为管理标签；门禁仅依权限点（token） |
| 项目 | 列表、概览、创建/删除、设置 | 可见性与操作由工作区/项目级权限点控制 |
| Chat | 会话、模型选择、流式消息、附件 | 页面级访问权限；用量与限流来自资源策略，不设独立 Chat 配额 |
| Notebook | 任务列表与详情、线程/上下文/产物、源库切换 | 页面级访问权限；源库为单一上下文，切换即清空并重拉 |
| Files | 库与文件、上传、AI Ready、库切换 | 使用 vs 管理 分离；库切换不混上下文 |
| Agents | 列表、详情、Keys | 使用 vs 管理 分离 |
| Endpoints | 列表、详情、限额、启停/轮换 | 使用 vs 管理 分离 |
| 资源策略 | 端点/智能体策略、访问模式、主体覆盖、限额、生效摘要 | 单一入口；策略解析顺序：主体覆盖 > 资源覆盖 > 项目默认 |
| 成员 | 人员、加入请求、分组与成员生命周期管理 | 查看 vs 管理 分离 |
| 凭据 | 列表、创建/轮换/删除 | 仅展示元数据，不展示密钥值 |
| 审计与用量 | 审计日志、用量统计、成本与明细过滤 | 只读、可过滤、可追责 |
| 运行观测与资源治理 | Runtime 观测、资源策略执行证据、审计与用量追踪 | 服务于项目级资源治理与审计，不提供发布编排或 DevOps 能力 |
| 设置 | 通用配置、运行时偏好、删除项目 | 项目级管理权限 |
| 邀请与加入 | 通过链接接受/拒绝加入项目 | 与成员模块的审批与列表一致 |

### 2.3 明确不在范围内（防范围蔓延）

- **文件级策略**：只做资源级策略，不做单文件级。
- **Chat/Notebook 独立配额**：用量与限流来自端点/文件库/智能体策略，不单独设 Chat/Notebook 配额维度。
- **角色名参与鉴权**：运行时门禁只认**权限点**；角色/分组名仅为治理标签，不参与鉴权逻辑。
- **大规模性能与长稳**：性能与长稳压测单独规划，不混入功能迭代门禁。
- **E2E 覆盖后端鉴权**：E2E 验证前端门禁与交互契约；与真实鉴权/边缘联调不纳入默认 E2E 范围。

### 2.4 产品术语（概念统一）

- **Notebook**：任务式智能体工作流模块；对外命名统一，禁止引入「Studio」「Task Center」等别名。
- **Files**：项目文件管理；路由与 UI 命名统一。
- **Inputs / Artifacts**：仅限 Notebook 运行时（输入上下文、产出物）使用。
- **发布（Release）**：不是仅指前端页面上线；在本产品中，发布指“运行时配置 + 发布证据 + 治理决策”达到可放量状态。具体包含：运行路由发布（alias/combo）、门禁执行与证据产出、策略放行与升级处置（override/escalation/incident）。

具体术语表见合约。

## 三、设计原则（思想与方法论）

### 3.1 权限与门禁：Token 唯一

- **思想**：前端与后端共用同一套**权限点（permission token）** 作为门禁语言；不引入角色名、分组名作为运行时判断依据。
- **方法论**：路由与操作级门禁只使用合约中定义的权限点；角色/分组仅用于治理展示，不参与「能否访问」的逻辑。
- **权威**：403/401 以后端为准；前端门禁用于隐藏/禁用与友好提示，不替代后端鉴权。

### 3.2 工作区/项目上下文：URL 为真相源

- **思想**：当前工作区与项目由**地址栏**表达；任何状态栏、面包屑、侧栏选择器都应与 URL 一致，而非反过来用本地状态覆盖 URL。
- **方法论**：工作区切换应清空项目上下文并回到项目列表；项目切换应反映在 URL 并进入概览；深度链接与浏览器前进/后退应正确反映并同步到应用状态。

### 3.3 视觉与交互：设计系统唯一来源

- **思想**：色彩、间距、圆角、阴影等视觉与布局规则来自**单一设计系统**；禁止在页面或组件内写死与设计系统无关的数值或色值。
- **方法论**：专业、克制；主行动色仅用于链接/主按钮/高亮；AI 类视觉仅用于明确 AI 标识；阴影仅用于浮层。具体 token 与数值以设计系统文档为准。

### 3.4 路由与参数：安全校验不可省

- **思想**：来自 URL 的工作区/项目标识是**不可信输入**，必须校验后再用于鉴权或请求；未经校验不得用于权限判断或服务端请求。
- **方法论**：所有依赖工作区/项目参数的路由必须先做参数校验；校验失败时呈现明确错误态，禁止用类型断言或默认值绕过。

## 四、架构原则（概念与分工）

### 4.1 状态与数据分工

- **思想**：认证与当前上下文、服务端数据、UI 状态应有清晰边界；URL 表达「用户正在看哪里」，不应被内存状态覆盖。
- **方法论**：认证与上下文与 API 鉴权保持同步；服务端数据通过可缓存、可失效的机制获取；新路由应提供加载态与错误边界，避免白屏或未捕获异常。

### 4.2 页面与组件分工

- **思想**：复杂页面由「谁负责数据与状态、谁负责展示」分工明确；业务逻辑集中、展示组件尽量无状态。
- **方法论**：父级负责拉数与门禁，子级通过约定接口消费；通用能力（弹窗、骨架、表格选择等）复用而非每页重写；接口错误与异常有统一处理与兜底，避免整页崩溃。

### 4.3 路由与门禁契约

- **思想**：受权限保护的壳内路由与项目列表页是**契约对象**：必须使用合约内权限点、必须做参数校验、必须有可自动检查的测试覆盖（正常、非法参数、无权限）。
- **方法论**：项目列表页不得以「已登录即可」作为门禁；权限判断逻辑中不得通过短路合并多个权限调用，导致调用顺序随条件变化（易引发运行时错误）。具体检查项与执行方式见合约。

## 五、质量与安全（思想）

### 5.1 类型与静态约束

- **思想**：生产代码保持强类型，避免「任意类型」削弱契约与重构安全性。
- **方法论**：禁止在生产代码中引入未约束的任意类型；未使用项应显式标记或移除。具体规则由工程规范与静态检查定义。

### 5.2 测试与契约

- **思想**：关键路径与契约有自动化保障；测试选择器稳定、不依赖易变的文案或样式。
- **方法论**：单元与 E2E 覆盖关键业务与门禁；新/改受保护路由或项目列表页必须通过门禁契约检查；API 契约变更后类型与客户端约定需同步。具体工具与阈值见工程规范。

### 5.3 安全

- **思想**：敏感信息不进入 URL/日志/前端持久化；流式或长连接优先使用短期凭据而非长期令牌；用户内容（如 Markdown 中的外链）需受信任域名约束；生产环境不启用仅用于开发的 mock 能力。
- **方法论**：危险操作（撤销 Key、轮换凭据、删除资源等）须二次确认，且错误/审计可追溯请求标识。具体实现与配置见安全相关合约与工程规范。

## 六、国际化（思想与方法论）

- **思想**：用户可见文案有**唯一来源**，多语言结构一致，便于维护与扩展。
- **方法论**：所有界面上的标题、按钮、提示、占位符、空状态等均来自国际化配置，不硬编码；同一含义全项目共用同一 key；通用与模块专属命名空间分离。具体文件结构与配置约定见 i18n 规范；非约定修改需评审。

## 七、禁止事项与防漂移清单

以下行为视为违反宪法，应避免或先修宪再实施：

1. **权限**：用角色名/分组名做运行时门禁；或引入未在合约中定义的权限点。
2. **范围**：在未修宪前提下，增加「文件级策略」「Chat/Notebook 独立配额」或将角色名当作鉴权依据。
3. **路由**：对工作区/项目参数不做校验或使用类型断言；受保护路由缺少门禁契约要求的测试覆盖。
4. **设计**：使用设计系统外的颜色/阴影/间距，或为营销目的引入高饱和、强品牌化的全局样式。
5. **术语**：在路由或产品文案中用 Notebook/Files 以外的主模块名，或混淆 Inputs/Artifacts 的适用范围。
6. **类型**：在生产代码中引入未约束的任意类型。
7. **i18n**：新增用户可见文案不纳入国际化或破坏多语言结构一致。
8. **契约**：新/改受保护路由或项目列表页在未通过门禁契约检查前合并。

## 八、宪法修订

- 本文档的修订应经过**评审与合意**，并保留修订历史（日期与要点）。
- 合约与规范与本宪法冲突时，以本宪法为上位；合约与规范应随后修订以对齐宪法。
- 新成员或外包协作前，应阅读本宪法及所引合约与规范，确保产品目标、设计风格与功能范围不漂移。
